## Implementation details and limits

- All existing secrets are validated before any new secret is published. A read-only SQLite inspection prevents replacements if records/events exist and fails closed if the database cannot be inspected.
- Missing secrets on an unprotected fresh setup are generated independently. Same-directory private temporary files are flushed/fsynced and atomically hard-linked into final paths without overwriting an existing secret. The returned KeyRing is loaded from persisted bytes.
- Existing certificates are checked for a matched RSA-2048 key, SHA-256 self-signature, valid dates and configured typed SANs. Missing/invalid/incomplete TLS identities require explicit renewal; ordinary startup never silently changes a previously present certificate.
- Explicit renewal generates a new RSA key/certificate and atomically replaces each TLS file, without loading or modifying application secrets. The two TLS files cannot form one filesystem transaction; an interruption between publication steps is detected as an unmatched/incomplete pair on next startup and requires explicit renewal. Launcher initialization remains serialized before server threads as specified.
