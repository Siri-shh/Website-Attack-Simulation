## Bounded implementation strategy

1. In-process smoke uses isolated temporary data, production initialization/seeds and packaged templates, not the existing conftest template stubs. Request helpers always use HTTPS base URLs, obtain the current form CSRF through GET, and submit normal form data without following credential POST redirects. This checks route integration; actual certificate verification belongs to the Docker client.
2. A normal Bob route flow creates a new record and edits that record. Read the persisted row after each POST to compare the page's complete ciphertext, nonce, hash, signature, three UTC timestamps, byte sizes, version and six-decimal millisecond timing values against actual saved fields. Assert creation timestamp survives editing, version increments, new cryptographic evidence is generated, and repeated detail GETs preserve every saved row field and displayed evidence/timings. Reload keys and app factories from the same temporary directory to check persistence without resetting it.
3. A second route flow performs five ordinary failed Bob logins, each with fresh CSRF, then succeeds and requests Alice's existing record. Assert 401/303/403 outcomes and new R2/R3/R4/R5 alerts linked to the actual signed events, source IP, Bob identity and successful session. Do not insert alerts or audit rows directly. Assert the denial page and Bob list contain none of Alice's plaintext or crypto/timing evidence. Separate console authentication checks reject a user login and accept admin.
4. Through the normal admin CSRF form, block the Bob source. The existing authenticated Bob cookie must immediately yield 403; admin snapshot/dashboard remain usable even from that blocked peer. Check the signed blocked_request context. Recreate apps/keys while deliberately retaining that block to demonstrate persistence, then remove it through the normal admin form and reuse the Bob cookie successfully. Record/alert identities and saved record evidence survive that recreation.
5. `tests/docker_smoke.py` stays an independent Requests/stdlib client with no `security_lab` or framework imports and no server-written event access. Required arguments are `--url`, `--console-url`, `--ca`, plus finite positive bounded wait timeout defaulting to 10 seconds. Every request supplies the CA path, a finite timeout and explicit redirect handling. Requests Session keeps ordinary cookie/CSRF state; no `verify=False`. Catch request/parse/check failures with concise nonsecret diagnostics and nonzero exit. Print only record IDs, event IDs, alert IDs and check outcomes; do not print passwords, cookie values, private keys, form bodies or opaque session references.
6. Docker uses separate Bob/Alice/admin sessions from the `.10` client to `.20` server. Read Alice's own seed record to collect owner evidence privately, then check Bob denial omits it. Use a baseline of event/alert IDs before the five failures so old findings cannot satisfy new cascade checks. Create/edit/refresh a Bob record through real forms, parse full evidence/timestamps/timings from HTML, and compare the complete evidence snapshot across repeated reads. Validate decoded Base64 sizes and hash/signature syntax; exact DB-to-HTML agreement is covered in-process and by controller persisted-state checks.
7. Poll `/api/snapshot` with a monotonic deadline and a short bounded interval (approximately 0.25–0.5 seconds), stopping immediately once the needed observations exist. Capture must remain running without error. Resolve every alert evidence event ID against observed snapshots; collect snapshots across phases so the API's newest-100 bound cannot hide earlier observations. Verify each application event's `signature_valid` is true and packet evidence uses null signature validity. R2 has the five actual failed login events; R3 links R2 plus the successful login; R4 links the actual Alice-record denial; R5 links R2/R3/R4 and the same successful session, with the union of seven application events.
8. The root's harmless HTTPS preflight and explicit five-port socket probe precede the cascade. Validate an R1 in the current live capture domain whose evidence is incoming connection_attempt events from `172.29.0.10` to `172.29.0.20`, includes ports 8443/8444/8001/8002/8003 within 30 seconds, and has real capture IDs/frame numbers. Do not require a second new R1 after repeating an already-crossed window. R2–R5 must be new and tied to this smoke's outcomes. A rerun inside an existing 60-second Bob failure window may not recross the R2 threshold; report that state and let the window age rather than resetting runtime evidence.
