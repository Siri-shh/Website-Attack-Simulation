## Signed session context

- Successful storage login: login_success / login_ok; canonical authenticated username and the freshly generated session_ref. Successful console login: admin_login_success / console_login_ok; canonical admin username and its freshly generated session_ref. Neither event carries the superseded session_ref or a cookie value.
- Credential or role failure: login_failure / login_denied, or admin_login_failure / console_login_denied; attempted username after strip/lower, session_ref=null. Clear the whole previous session before rendering the 401 response; a new anonymous CSRF token may then be generated for the login form. Never attach the previous authenticated account or session_ref to that failure.
- Authenticated storage blocked_request: username and session_ref are the current authenticated storage account/context; outcome=blocked_request. An anonymous or wrong-role session supplies null username and null session_ref. Capture this context before returning 403; blocking does not itself log out or mutate the session. Never obtain the username from submitted form data or the source address from forwarding headers. Apply admission before every storage request; there is no console admission hook.
- Authenticated successful logout: capture the current username/session_ref, enforce CSRF, append signed logout with outcome=logout, then clear the session and redirect 303 to /login. The logout event carries the departing reference even though the response leaves no authenticated identity. A missing/incorrect token returns 400 without clearing identity or emitting logout. Protect logout with require_login(required_role); unauthenticated logout redirects to /login without a logout event. Storage admission still takes precedence for a blocked storage peer.
- CSRF rejection is separate from credential failure: it emits no login-failure event and does not clear an already authenticated session. Every signed auth event retains the exact approved payload field set; destination uses configured server IP and the app's own configured port, record_id=null.

These context rules implement the spec's attempted-username versus authenticated-account distinction and preserve login/session evidence needed by later rules. Console events remain excluded from R2/R3 by their admin kinds/outcomes, rather than by removing session context.
